# Deploying SwiftlyS2 and plugins

Administrators can open **Deploy SW2 Platform** or **Deploy Plugin** beside schedule management on the instance list. Both default to **All current instances** across all configured nodes and pages, independently of list filters or existing checkboxes. Select the package once and review one deployment batch. To narrow the scope, switch explicitly to **Selected instances**, which retains the list's existing selection and permits editing it. These actions use the administrator's node file context and the existing direct/proxy transfer settings.

1. Stop the affected game instances manually and reserve a maintenance window. Keep them stopped throughout deployment. The workflow does not stop, start, restart, or reload servers. Because launcher scripts can hide shared paths, the preview conservatively includes every instance on each selected node; confirm this affected list before applying.
2. Choose a local ZIP (up to 100 MiB) or folder (up to 250 MiB expanded, 10,000 entries). Platform packages accept `game/csgo/`, `csgo/`, `addons/swiftlys2/`, or a single enclosing release folder. Only SW2 platform files and its Metamod descriptor are accepted. Plugin packages must contain the plugin files directly or under the matching plugin directory, optionally within `addons/swiftlys2/plugins/`.
3. Both modes automatically use the shared CS2 root `/mnt/steam/cs2/game/csgo` on each node; the dialog displays it without per-node directory inputs. For plugins, check the plugin directory name, such as `PreAimMode`. The destination becomes `addons/swiftlys2/plugins/PreAimMode/` exactly once. Install SW2 before deploying its plugins.
4. Inspect the normalized manifest and click **Inspect package and preview deployment**. Existing configuration, data, translations, gamedata, and bundled platform plugins are protected by default. Missing defaults are installed. To replace protected existing files, select the explicit replacement option and generate a fresh preview.
5. Review instance counts, unique destinations, per-node affected instances, exclusions and the backup choice. **Back up before deployment** defaults on; disabling it is independent of protected-file replacement and explicitly warns that no recovery backup will be created. Confirm the refreshed batch once and start deployment. Instances on one node share one deployment, so their shared game directory receives one transfer. Offline nodes, incomplete inventory, invalid directories, and running affected instances block their own targets; other approved eligible targets can proceed. With backups enabled, replacements and loader edits are backed up first into `<game-directory>/.mcsm-deploy-backups/<unique-id>.zip`; failure prevents overwrite. With backups disabled, neither backup trees nor ZIPs are created and the target result identifies that policy. The interface reports queued, transferring, extracting, verifying, and terminal results. Successful transfer alone does not count as deployment success: extraction must finish and all written file lengths must match the manifest. Platform deployment also verifies an idempotent SW2 loader entry in `gameinfo.gi`; plugin deployment does not edit it.
6. Review results, then start servers manually when ready. **Files deployed** does not mean the runtime has been activated. Retrying failed targets requires a fresh preview and confirmation; successful targets remain completed.

An incomplete node inventory has unknown coverage and never authorizes file writes on that node. The batch freezes its reviewed targets and backup policy; new instances are not enrolled automatically, and a changed affected-instance set requires another preview before that shared destination can be written. Retry refreshes only unresolved nodes, including recovered inventory, for renewed review. Changing scope, package, plugin name, protected-file replacement or backup settings invalidates the preview and approval.

Keep the page open during deployment. Cancel stops subsequent steps and active transfers; extraction already started can complete. A timeout or error may leave partially replaced files. When backups were enabled, the backup path remains visible: use the administrator node file manager to inspect the ZIP and restore its corresponding original paths before starting the game. Each backup ZIP contains a unique-ID directory with the original paths relative to `game/csgo` beneath it; restore that directory's contents to the game directory. The same uncompressed backup tree remains beside the ZIP. No-backup targets have no automatic recovery copy. There is no automatic rollback. Generated upload ZIPs and any backup trees/ZIPs remain in the game directory until the administrator removes them.

Directory listings on older nodes provide normalized paths but may not resolve filesystem symlink aliases. Use the same actual game directory spelling for shared targets. The existing protocol does not lock other administrators out; do not start games or edit deployment files concurrently. Unsupported nodes fail during preflight and are not upgraded automatically.
